## 1. 总体架构

### 1.1 进程与职责划分

```
┌─────────────────────────────────────────────────────────┐
│ Renderer (React)                                        │
│  五个模块页面 + 设置页 + 任务中心                        │
│  只负责：展示计划、收集确认、渲染进度、展示报告           │
└──────────────┬──────────────────────────────────────────┘
               │ IPC (typed channels)
┌──────────────▼──────────────────────────────────────────┐
│ Main (Node)                                             │
│  ├─ ScanEngine      递归扫描、分类、匹配（纯函数）       │
│  ├─ MediaProbe      ffprobe 探测容器/编码/时长/方向      │
│  ├─ TaskCenter      并发调度（默认 5，1–20 可配）        │
│  ├─ Executors       clean / rename / poster / nfo / merge│
│  └─ SettingsStore   electron-store 持久化配置            │
└──────────────┬──────────────────────────────────────────┘
               │
┌──────────────▼──────────────────────────────────────────┐
│ Worker Threads / 子进程                                  │
│  图片转码 (sharp)、截帧 (ffmpeg)、合并 (ffmpeg)          │
└─────────────────────────────────────────────────────────┘
```

关键原则：

- **计划与执行分离**：所有模块拆成 `createPlan() → executePlan()` 两步。`createPlan` 是纯函数（可单测、只读文件系统），`executePlan` 只在用户确认后运行。
- **重活不进主进程**：ffmpeg/sharp 一律放 Worker Thread（sharp、CPU 密集）或子进程（ffmpeg 命令行），主进程只做调度，避免 UI 卡顿。
- **类型单一来源**：共享类型放 `src/shared/types.ts`，main / preload / renderer 三端引用，消灭现状中 `scanner.d.ts` 与 `index.d.ts` 的双份定义。

### 1.3 技术选型决策

| 领域               | 选型                                     | 理由与注意事项                                                                                                                                                 |
| ------------------ | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 媒体探测/截帧/合并 | `ffmpeg-static` + `ffprobe-static`       | 随包分发二进制，无需用户安装；electron-builder `asarUnpack` 配置必须包含二进制，且打包后要修正路径（`app.getAppPath()` 替换 `app.asar` → `app.asar.unpacked`） |
| 图片转 JPG         | `sharp`                                  | 原生模块，`electron-builder install-app-deps` 会按 Electron ABI 重编译；CI 双平台分别构建，无交叉编译问题                                                      |
| 并发池             | 自研轻量池（`p-limit` 思路 + 取消令牌）  | 需求只要 1–20 并发 + 进度回调，不引重型依赖；视频合并单独一个池（并发 1，避免磁盘/CPU 打满）                                                                   |
| 配置持久化         | `electron-store`                         | 存并发数、OpenRouter token、模型列表、正则模板、prompt 模板                                                                                                    |
| 前端状态           | `zustand`                                | 轻量，按模块分 store，避免 Redux 样板                                                                                                                          |
| 拖拽排序           | `@dnd-kit/core` + `@dnd-kit/sortable`    | 自由组合合并排序用，无障碍好                                                                                                                                   |
| 视频播放           | 原生 `<video>` + 自定义控制条            | 详情页拖动时间轴截图，无需第三方播放器                                                                                                                         |
| 路由               | 状态切换即可（单窗口五页面）             | 不引 react-router，侧边栏受控导航                                                                                                                              |
| UI 体系            | 自研 macOS 风格设计令牌（CSS variables） | 见 §2                                                                                                                                                          |

### 1.4 通用"扫描→预览→确认→执行→报告"框架

所有模块共用一套契约，这是冻结稿 §2.3 的硬性要求：

```ts
// src/shared/types.ts（示意）
interface PlanBase {
  module: 'clean' | 'merge' | 'rename' | 'poster' | 'nfo'
  createdAt: string
  stats: Record<string, number>
  deletes: DeleteItem[] // 永久删除清单：路径、体积、原因
  changes: ChangeItem[] // 移动/改名/新建
  conflicts: ConflictItem[] // 需人工裁决
  risk: 'normal' | 'danger' // danger 触发确认词
}
interface Report {
  planId: string
  succeeded: ChangeItem[]
  failed: { item: ChangeItem; error: string }[]
  deleted: DeleteItem[]
  durationMs: number
}
```

- **风险升级规则**（冻结稿 §2.6）：删除数 > 50 或删除体积 > 1GB 或工作区无视频 → `risk: 'danger'`，确认对话框要求输入确认词（如输入"永久删除"）才放行。
- **取消语义**：执行中可取消；已完成的写操作不回滚（报告中如实列出），未开始的跳过。
- **重名处理**（冻结稿 §2.7）：执行层 `fs-ops.ts` 统一做 `name (1).ext` 递增，任何模块不各自实现。

## 2. UI 设计方案（macOS 风格）

设计目标：Windows / macOS 双端像素级一致，现代、克制、通透。

- **布局**：左侧 220px 半透明侧边栏（毛玻璃 `backdrop-filter`），右侧内容区；窗口 1200×800 起步，最小 960×640。
- **设计令牌**（CSS variables，支持浅色/深色自动跟随系统）：
  - 色板：系统蓝 `#0A84FF` 为主色；危险红 `#FF453A`；成功绿 `#30D158`；警告橙 `#FFD60A`
  - 灰阶：macOS 语义灰（`--label-primary/secondary/tertiary`、`--fill-quaternary` 等）
  - 圆角：卡片 10px、按钮 6px；阴影：两级（卡片 / 弹层）
  - 字体：`-apple-system, "SF Pro Text", "Segoe UI", "PingFang SC"` 栈
- **核心组件**：TrafficLight 留白（`titleBarStyle: 'hiddenInset'`）、侧边栏导航项、卡片、统计条、计划三栏预览、风险确认弹窗、进度任务中心（右下角抽屉）、Toast。
- **窗口配置**：`titleBarStyle: 'hiddenInset'`（mac 保留红绿灯）、Windows 用 `hidden` + 自绘标题栏按钮，保证双端观感一致。
- **交互细节**：列表行 hover 浮起、按钮按压缩放 0.97、计划执行骨架屏、删除项红色删除线但可展开看原因。

## 3. 共享基础设施实现步骤（阶段 0，先行）

> 这是五个模块的地基，全部带单测。

1. **类型收敛**：新建 `src/shared/types.ts`、`constants.ts`；把 `scanner.mjs` 迁移为 `src/main/core/scanner.ts`（TypeScript 化），删除 `scanner.d.ts` 与 preload 里的重复 `ScanPlan` 定义。同步修复 Windows 路径分隔符问题。
2. **fs-ops.ts**：`permanentDelete()`（含隐藏内容目录保护：删除空目录前 readdir 检查是否残留隐藏项）、`moveWithCollision()`（自动 `(1)` 后缀）、`rename()`；全部返回结构化结果，**执行层禁止绕过此文件直接调 fs 写接口**（加 ESLint `no-restricted-imports` 规则）。

5. **settings**：`electron-store` schema（并发数、OpenRouter token、模型列表默认含 `deepseek/deepseek-chat`、`openai/gpt-5.6-luna` 等、正则模板、prompt 模板）。
6. **UI 骨架**：侧边栏五模块导航 + 设置页 + 任务中心抽屉 + 通用 PlanPreview/ConfirmDialog 组件；现有 `App.tsx` 扫描预览迁入 `CleanPage`。

## 4. 模块一：目录清理、图片匹配与解散子目录

> 对应冻结稿 §3。现有 scanner 已覆盖约 60%，本阶段补全规则并接入执行层。

### 4.1 createCleanPlan(root) 规则补全

- 匹配严格**同层**：先按目录分组，再组内做视频×图片匹配（现状是按全局归一化名匹配，需改为按目录桶）。
- 归一化保持现状：忽略大小写、空格、`-`、`_`、`.`、`-poster` 后缀；不清除年份/分辨率等语义片段。
- 一视频多图裁决链：`-poster` 图优先 → 与视频名完全同名（仅去扩展名）次之 → 仍多候选 → `conflicts` 标红，预览页提供单选手选；选中者命名为 `<视频基名>-poster.jpg`（非 jpg 的进 sharp 转换队列），落选者入删除清单。
- 一图多视频：歧义删除（现状已实现），相关视频标 `poster: none`。
- 上移计划：所有保留项 `from → <根目录>/<name>`；重名在预览期就标注 `→ name (1).ext`（预览时按目标集合静态推算，执行时以 `fs-ops` 为准二次兜底）。
- 空目录删除计划：自底向上标记将变空的目录；含隐藏项的目录排除。

### 4.2 executeCleanPlan(plan, choices)

顺序严格按冻结稿：删除（清单确认后）→ 上移 → 重名解决 → 删空目录 → 报告。每步经任务中心发进度。

### 4.3 验收用例（扩充 test/）

- 冻结稿示例目录树（图片 3/7 删除、图 片 4 空格匹配、6-poster 匹配）

## 5. 模块四：Poster 封面管理（先于合并做，产出被归档复用）

> 对应冻结稿 §6。之所以排第二：NFO/合并都消费 poster。

1. **视频列表页**：缩略图网格（有 poster 显示 poster；无 poster 显示灰占位 + "生成候选"按钮，或批量生成）。
2. **截帧服务**：`ffmpeg -ss <t> -i <f> -frames:v 1 -q:v 2`，5 个时点 10/30/50/70/90%；输出到 `app.getPath('temp')/msd-frames/`，不进工作区；任务中心按配置并发执行。
3. **详情页**：候选图横向排列、内嵌 `<video>` 播放、时间轴拖动 + "截取当前帧"按钮（renderer 用 `canvas.drawImage(video)` 抓帧，精确到用户所见帧，比 ffmpeg seek 更直观；非 seekable 编码回退 ffmpeg 按秒截）。
4. **保存**：选定唯一封面 → sharp 转 JPG → 写 `<视频基名>-poster.jpg` → 旧关联图/落选候选入删除清单 → 确认后永久删除 → 报告。
5. **体积防护**：单帧输出限宽 1920（`-vf scale='min(1920,iw)':-2`），避免 4K 帧撑爆内存。

## 6. 模块三：批量重命名

> 对应冻结稿 §5。三种模式共用同一预览/校验/执行管线。

### 6.1 通用管线

`原始列表 → 模式变换器 → newName 预览表（可编辑单元格）→ 校验器 → 确认 → 执行（视频+poster 成组改）`

- 组处理：视频与其 poster 为一组；视频改为 `X.ext`，poster 同步 `X-poster.jpg`。
- 校验器：非法字符 `[\\/:*?"<>|]`、空名、长度（Win 260 路径余量）、大小写冲突（mac 不敏感文件系统）、组间重名 → 行级标红 + 禁止执行。
- 执行：两遍改名（先全改临时名再改目标名），规避 A→B、B→A 互换死锁。

### 6.2 三个变换器

1. **纯序号**：排序键（标题/大小）× 升降序 → 位数（1–6 位补零）→ 分隔符（`.`/`、`/空格，默认 `.`）→ `<序号><分隔符><原标题>`。
2. **正则清洗+序号**：规则 = `{pattern, replacement, flags}` 列表；内置常用模板（`@xxx` 尾巴、`【...】`、`[...]`、分辨率/年份噪音）；正则测试器（输入样例实时高亮命中）；用户规则可保存到设置。
3. **AI 重命名**（OpenRouter）：
   - 设置页：Token、模型下拉（默认 `deepseek/deepseek-chat`、`openai/gpt-5.6-luna`、可自定义添加）、并发与超时。
   - Prompt 模板（可编辑，变量 `{{parentFolder}}` `{{fileName}}` `{{extension}}`），默认模板要求模型**只返回 JSON 数组** `[{"from":"...","to":"..."}]`，并在 system 里锁死输出格式与命名约束。
   - 调用走主进程 `fetch`（OpenRouter 兼容 OpenAI chat/completions，`POST https://openrouter.ai/api/v1/chat/completions`，header 带 `Authorization: Bearer <token>`、`HTTP-Referer`、`X-Title`）；分批发送（每批 ≤ 50 个文件名）控制 token；**只发文件名与父目录名，不发任何文件内容**。
   - 结果校验：JSON 结构 → 每个 `to` 过校验器 → 失败项回退保留原名并标黄 → 用户确认后执行。

### 6.3 仅改扩展名为 .mp4

独立小工具入口：列出非 `.mp4` 视频 → ffprobe 探测真实容器 → 容器非 MP4 的项红色警告"仅改后缀不转封装，部分播放器可能无法识别"→ 需逐项勾选或全选确认 → 执行 rename。

## 7. 模块五：NFO 与独立归档

> 对应冻结稿 §7。纯文件操作，逻辑最轻，与重命名共享校验/确认组件。

1. `createNfoPlan(root, options)`：每个视频一组（视频 + 其 poster），目标目录 `<工作区>/<视频基名>/`（或用户指定输出根）；检测目标目录已存在/已含文件 → 冲突标红（策略：跳过或 `(1)` 后缀，预览可选）。
2. NFO 渲染：冻结稿 §7 的 XML 模板，`title` = 视频基名、`poster` = `<基名>-poster.jpg`、`actor.name/role` = **工作区根目录名**（可全局覆盖为用户输入）；XML 转义 `& < > "`；无 poster 时省略 `<poster>` 行并在预览标注。
3. 执行顺序：建目录 → 移动视频+poster → 写 NFO → 校验（XML parse + 三个文件存在性 + 名实一致）→ 报告。
4. 验收：Kodi/Jellyfin/Emby 兼容 = 合法 XML + UTF-8 + 字段名冻结即可，不联网。

## 8. 模块二：视频物理合并（最后做，风险最高）

> 对应冻结稿 §4。

### 8.1 列表与选择

- 全量视频卡片：缩略图（复用模块四截帧）、标题、路径、时长、大小、分辨率、方向、容器、v/a 编码、帧率（probe.ts 提供）。
- 排序：标题/大小切换；四种模式 Tab：全合并 / 横屏 / 竖屏 / 自由组合（多选 + dnd-kit 拖拽排序）。

### 8.2 兼容性判定与两条管线

对所选视频按首个片段的参数集合（容器、v 编码+profile+level、分辨率、帧率、pix_fmt、a 编码+采样率+声道）逐项比对：

- **全兼容 → 无重编码拼接**：生成 concat 清单 `file '...'` → `ffmpeg -f concat -safe 0 -i list.txt -c copy out.mp4`（速度快、无损、内存占用极低）。
- **不兼容 → 转码统一**：统一目标参数（H.264 + AAC、分辨率取首个横/竖片段、fps 取源最大值的公约）→ **逐段转临时中间文件**（并发受合并专用池限制，默认 1–2，避免内存/磁盘爆）→ concat 拼接 → 删临时文件。
- 预览页展示：兼容结论、是否转码、预计输出大小（兼容=Σ源大小；转码=按目标码率×总时长估算）、目标盘可用空间（不足则禁止执行）。

### 8.3 性能与安全约束

- 单 ffmpeg 子进程 + `-threads` 交给 ffmpeg 自适应；转码用 `-preset veryfast`；进程优先级 `nice`（mac）/ `BELOW_NORMAL_PRIORITY_CLASS`（win）。
- 进度：解析 ffmpeg `-progress pipe:1` 的 `out_time_ms` 换算百分比推送任务中心；支持取消（kill 子进程 + 清临时文件）。
- 输出校验：ffprobe 重读输出（可打开、时长≈Σ源时长±1s、同时含 v/a 流）。
- **校验通过才进入源删除清单**（源视频 + 关联 poster），在计划中单列"合并后永久删除源片段"区域，二次确认；校验失败保留全部源文件并出错误报告。
- 输出命名：冻结稿四种模板，落工作区根目录，重名走 `(1)`。
